# خارطة طريق تنفيذ Moudie NetPlay للإنتاج

## القرار المعماري

### 1. لا يعتمد التطبيق على Matsu Player

لن أدمج Matsu Player أو أستخرج منه ملفات. لا يظهر مصدر رسمي أو ترخيص يسمح بإعادة تضمينه، وتاريخه المتاح يشير إلى تطبيق مستقل قديم. البديل الصحيح هو **مضيف Libretro أصلي** داخل التطبيق، يُبنى ويتحكم فيه Moudie ويشغّل النوى بتراخيصها الفعلية. هذا يتطلب تحويل تطبيق Expo من اعتماد JavaScript فقط إلى Expo Development Build/React Native أصلي مع Android NDK وطبقة JNI أو JSI.

### 2. نوى المحاكيات المقترحة

| النظام | النواة المقترحة | حالة الترخيص/التشغيل | قرار التنفيذ |
|---|---|---|---|
| PlayStation 1 | PCSX-ReARMed عبر Libretro | GPLv2، محسن لـ ARM، يحتاج BIOS صالحًا لأفضل توافق | يبدأ به مع Famicom لأنه مناسب للهاتف. |
| PlayStation Portable | PPSSPP عبر Libretro | GPLv2، يحتاج ملفات مساعدة ويستفيد من Vulkan | مرحلة منفصلة بعد اختبار أجهزة Android فعلية. |
| Famicom/NES | FCEUmm عبر Libretro | حفظ وحالات حفظ وNetplay وmultitap حتى 4 في ألعاب محددة | يحل محل التنفيذ التجريبي الحالي بعد توحيد المضيف الأصلي. |
| Sega | Genesis Plus GX عبر Libretro | دعم واسع لنظم Sega وFrameskip وإعدادات منطقة | يدمج في الطبقة الموحدة مع حدود ألعاب Sega الحقيقية. |
| Arcade | قرار قانوني قبل الدمج | FBNeo يفرض قيودًا غير تجارية؛ وMAME مشروع GPL وعلامته التجارية وROMs تتطلب عناية | لا أدمج أي نواة آركيد قبل مراجعة الترخيص ونموذج الربح. |

سيكون إدخال ROM أو BIOS من المستخدم فقط. لن يوزع Moudie ROMs أو BIOS ضمن التطبيق. لكل لعبة، يُخزن التطبيق تجزئة المحتوى والإعدادات ونسخة النواة، ولا يسمح بجلسة أونلاين إذا اختلفت بين اللاعبين. [1] [2] [3] [4]

## التصميم الحقيقي للغرف

يجب فصل “عدد أعضاء الغرفة” عن “عدد اللاعبين الذين تدعمهم اللعبة”. غرفة تضم عشرة أشخاص تعمل كلوبي PUBG: كلهم يدخلون، يتحدثون، يكتبون، ويعلنون الاستعداد؛ لكن شاشات اللعب لا تمنح مقعد إدخال إلا لعدد المنافذ الذي تدعمه اللعبة المختارة. لعبة تدعم لاعبين تعرض مقعدين و8 مشاهدين؛ لعبة Famicom multitap مدعومة تعرض أربعة مقاعد و6 مشاهدين. لا توجد طريقة صحيحة لتحويل لعبة قديمة ثنائية اللاعبين إلى عشرة لاعبين متزامنين من دون إعادة تصميم اللعبة نفسها.

```text
Lobby
  └── يختار المضيف: النظام + اللعبة + إعدادات النواة + المنطقة
       └── الخادم يتحقق: hash / core-version / firmware / منافذ اللعبة
            └── جاهز: اللاعبون الفعليون فقط
                 └── المضيف يبدأ: دخول متزامن + شاشة لعب سوداء
                      ├── اللاعبون: مدخلات + Rollback/Lockstep حسب النواة
                      └── المشاهدون: فيديو/صوت اللعبة + دردشة بلا إدخال
```

يتطلب ذلك `Game Capability Catalog` في الخادم، يُعرّف لكل نواة/لعبة: الحد الأقصى للمنافذ، نوع التزامن، دعم الحفظ، دعم المشاهدة، والحد الأدنى للأجهزة. لا تُقبل غرفة إلا بعد تطابق هذه القدرات.

## NetPlay الصحيح

لا يكفي Socket.IO لترحيل ضغطات الأزرار. لكل نواة يجب أن توفر طبقة NetPlay حتمية تشمل ترتيب الإطارات، إدخالًا متنبئًا، rollback عندما يتأخر إدخال، لقطات حالة دورية، وإعادة اتصال من دون تلف جلسة الحفظ. النوى لا تضمن أن واجهة Netplay الخاصة بـ RetroArch قابلة للاستدعاء تلقائيًا داخل تطبيق آخر؛ لذلك يجب إثبات التكامل عبر نموذج أولي لكل نواة بدل وعد موحد قبل الاختبار.

القرار هو البدء بمسار صغير قابل للإثبات: **Famicom لاعبان**، ثم PS1 لاعبان، ثم Famicom أربعة لاعبين حيث تدعم اللعبة multitap، ثم PSP/Sega. لا يُفتح وضع عشرة “لاعبين” في أي نظام إلا عند إثبات دعم اللعبة والنواة والبروتوكول له.

## الصوت والمشاهدة والدردشة

الصوت لعشرة أعضاء لا يستخدم mesh. ستنشر كل أجهزة الغرفة مسار صوت واحدًا إلى **LiveKit SFU** وتستقبل المسارات المطلوبة؛ وهذا يجنب الهاتف إنشاء تسع وصلات رفع. ويعمل **Coturn** كخدمة TURN/STUN خاصة مع رموز وصول قصيرة العمر تصدر من خادم Moudie؛ فلا نعتمد على STUN عام أو مفاتيح ثابتة على الهاتف. [5] [6]

المشاهد لا يجب أن يستلم مدخلات أو حالة المحاكي الكاملة. ينشر المضيف، أو جهاز مضيف مُنتخب، بث الفيديو والصوت للعبة إلى SFU باستعمال ترميز عتادي على الهاتف، ويتلقى المشاهد البث عبر LiveKit. عند تغيير المضيف أو سقوطه، تنفذ الغرفة انتخاب مضيف أو تنهي الجلسة برسالة واضحة؛ لا يمكن ضمان استمرار لعبة حتمية إذا اختفى الجهاز الوحيد الذي يملك حالتها من دون وجود مضيف سلطوي أو نسخ حالة مؤكدة.

تستمر الدردشة النصية عبر Gateway موثق بخادم Moudie، مع حدود طول وسرعة الإرسال، سجل تقارير وحظر، وRedis للحضور والـfan-out. لا توضع صلاحيات الغرفة أو رموز TURN أو مفاتيح LiveKit في التطبيق.

## البنية الدائمة

هذه ليست خدمة يمكن تشغيلها داخل صندوق تطوير مؤقت. النشر يحتاج خدمات دائمة وTLS وعناوين عامة ومراقبة:

| المكوّن | الدور |
|---|---|
| Mobile API + Auth | حسابات الضيوف والربط بالحسابات وإدارة الملفات وقواعد الغرف. |
| Realtime Gateway + Redis | حضور الأعضاء، ready checks، الدردشة، إشارات الجلسة، وrate limits. |
| MySQL/PostgreSQL | حسابات اللاعبين، الغرف، الحظر، المباريات، والتدقيق. |
| LiveKit SFU | صوت الغرفة وبث اللعبة للمشاهدين. |
| Coturn | عبور NAT عندما لا ينجح اتصال WebRTC المباشر. |
| مراقبة | مقاييس ping وpacket loss وFPS والجلسات الفاشلة وسجلات الأعطال. |

يصلح خادم مستمر مع Docker وخدمة TURN مستقلة لهذا الحمل. لا يوضع Coturn أو SFU داخل Expo أو في عملية Node.js نفسها. يتيح Coturn تشغيل STUN/TURN مع UDP/TCP/TLS ومصادقة مؤقتة؛ بينما يوضح LiveKit أن SFU هو النموذج الأنسب للمجموعات الأكبر من 2–3 أطراف. [5] [6]

## مراحل التنفيذ ومعايير القبول

| المرحلة | الناتج | معيار القبول |
|---|---|---|
| A: قانوني ومنصة | جرد تراخيص، سياسة ROM/BIOS، Android-first build | موافقة على GPL والتوزيع المفتوح للالتزامات، ومنع ROMs غير المرخصة. |
| B: هوية وغرف | ضيف + playerTag، حسابات Google، لوبي واستعداد وحضور | إنشاء غرفة وانضمام ومشاهدة وإعادة اتصال على جهازين فعليين. |
| C: بنية صوت | LiveKit + Coturn + رموز مؤقتة + مراقبة | 10 أعضاء صوتيًا مع اختبار شبكات Wi-Fi/4G وNAT مختلفة. |
| D: محرك موحد | Libretro host أصلي وحمل آمن للملفات وحفظ وإعدادات متحكم | Famicom محلي مستقر على مجموعة أجهزة مستهدفة. |
| E: NetPlay مدعوم | Famicom 2 ثم 4، ثم PS1 2 | جلسات متعددة تتجاوز اختبار فقد الحزم وإعادة الاتصال من دون desync. |
| F: الأنظمة الأخرى | PPSSPP وGenesis Plus GX بعد اختبارات توافق | تشغيل محلي مستقر أولًا، ثم NetPlay وفق حدود كل نواة. |
| G: مشاهدة وإطلاق مغلق | بث اللعبة وتقارير وحظر وتحليلات أعطال | beta محدودة، ثم فتح تدريجي بناءً على مؤشرات الأعطال والتأخير. |

## القيود الصريحة

لا يمكنني أن أعد بأن كل لعبة من كل نظام ستعمل بسلاسة على كل هاتف أو أن الاتصال لن يواجه أي مشكلة؛ اختلاف الألعاب، التراخيص، الأجهزة، الشبكات وNAT يجعل هذا وعدًا غير صحيح. ما أستطيع تنفيذه هو بناء بوابات قدرات واختبارات وFallbacks ومراقبة تمنع تشغيل المجموعات غير المدعومة وتكتشف الخلل وتتعافى منه بصورة منظمة.
